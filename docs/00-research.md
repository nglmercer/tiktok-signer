# 00 — Research

## Scope

This project uses TikTok's own WebView SDK for request signing. It does not reimplement
the signing algorithm.

## Connection flow

1. Discover a live channel from the rendered `/live` page.
2. Resolve `unique_id` to `room_id`.
3. Build the `/webcast/im/fetch/` query from one device preset.
4. Let `webmssdk.js` sign the request inside the WebView.
5. Replay the signed request with the session cookies and decode protobuf.
6. Build and sign the WebSocket URI, send `im_enter_room`, then process frames.

The HTTP fetch is the critical signed operation. The response supplies `cursor`,
`internal_ext`, `route_params`, and `push_server`.

## Authentication

An anonymous session currently receives HTTP 200 with an empty body from
`/webcast/im/fetch/`. A real `sessionid` cookie is required for the authenticated
flow. The same session cookies and User-Agent must be used for the WebSocket handshake.

## Query consistency

`browser_name`, `browser_version`, `browser_platform`, `os`, screen dimensions,
timezone, and language values must be generated by one `Preset`. Mixing values from
different presets causes silent rejection.

## WebSocket parameters

The signed response supplies route parameters. The client appends its own parameters,
including `cursor`, `internal_ext`, and a second `version_code` entry. Duplicate
query keys are intentional and therefore use ordered pairs rather than a map.

## Expiry

Signed parameters expire quickly, approximately 30 seconds. Do not reconnect with an
expired URI; repeat the complete signing flow. A rejected 200 handshake is detection,
not a transient transport failure.
