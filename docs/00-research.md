# 00 — Research

## Scope

The current live path uses TikTok's own page as the transport owner and does not depend on a
proprietary signing service. In parallel, the signing research track uses that page as a
sanitized oracle while building a reproducible native/headless implementation. See
`09-signing-research.md` for the confirmed boundary and current evidence.

## Connection flow

1. Discover a live channel from the rendered `/live` page.
2. Resolve `unique_id` to `room_id`.
3. Subscribe Rust to page-WebSocket IPC events.
4. Navigate the WebView to the selected live page.
5. Let TikTok's scripts sign and open their native WebSocket.
6. Relay binary frames to Rust and decode `WebcastPushFrame`.

TikTok's page performs room entry and heartbeats. Rust only observes the transport and
therefore needs none of the private signing logic.

## Authentication

The WebView can use a stored authenticated session. The page-owned transport also avoids
copying session cookies into an independently implemented WebSocket handshake.

## Query consistency

`browser_name`, `browser_version`, `browser_platform`, `os`, screen dimensions,
timezone, and language values must be generated by one `Preset`. Mixing values from
different presets causes silent rejection.

## Legacy direct-client path

The repository retains `/webcast/im/fetch/`, ordered query construction, and the direct
Rust WebSocket client for diagnostics. This path is not the default because TikTok can
silently reject the fetch with an empty HTTP 200 body.

## Expiry

For page-owned sockets, TikTok's scripts manage expiry and reconnection behavior. The IPC
relay follows each newly opened socket without storing or replaying signed parameters.
